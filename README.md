# RETRO Store

متجر إلكترونيات وأجهزة ريترو باللغة العربية، مبني باستخدام Next.js 15 وCloudflare Workers وD1.

## حالة الترحيل

هذا الفرع ينقل أساس المشروع من Supabase إلى Cloudflare:
- GitHub هو مستودع الكود وإدارة الإصدارات.
- Cloudflare Workers يستضيف تطبيق Next.js عبر OpenNext.
- Cloudflare D1 قاعدة SQLite للمنتجات والفئات والطلبات وعناصر الطلبات.
- الأسعار بالدينار العراقي (IQD)، وترتيب المنتجات والفئات عبر `sort_order`.
- الطلبات مخططة للدفع عند الاستلام، دون تسجيل حسابات للزبائن.
- حماية لوحة المالك ستُنفذ عبر Cloudflare Access بسياسة تسمح ببريد المالك فقط.

**تنبيه:** هذا الفرع يجهز البنية والترحيل الأولي، ولا يعني أن قاعدة D1 أُنشئت في حساب Cloudflare أو أن الموقع نُشر. يجب إكمال إعداد حساب Cloudflare وربط D1 ثم اختبار البناء والطلبات قبل الإنتاج.

## المتطلبات

- Node.js 20 أو أحدث.
- حساب Cloudflare مع Workers Free.
- مستودع GitHub متصل بـ Cloudflare Workers Builds أو Wrangler محلياً.

## إعداد Cloudflare D1

1. قاعدة `retro-store-db` موجودة مسبقاً؛ لا تنشئ قاعدة ثانية.
2. يحتوي `wrangler.toml` على معرّف القاعدة الحالي وربط `DB`.
3. من Console تأكد من وجود الجداول الخمسة الأساسية، ثم نفّذ `migrations/0002_inventory_triggers.sql` مرة واحدة قبل اختبار الطلبات.
4. بعد إعداد Cloudflare Access ومتغيرات المالك، شغّل الترحيلات عبر Wrangler عند استخدام سجل الترحيلات:

```bash
npx wrangler d1 migrations apply retro-store-db --remote
```

لا تنفذ `wrangler d1 create` لأن قاعدة البيانات موجودة بالفعل.

## التشغيل محلياً

```bash
npm install
npm run dev
```

لمعاينة التطبيق في بيئة Workers مع ربط D1:

```bash
npm run cf-typegen
npm run preview
```

## النشر

بعد إضافة قاعدة D1 وربطها والتحقق من المتغيرات:

```bash
npm run deploy
```

يمكن أيضاً ربط مستودع GitHub بمشروع Workers Builds ليتم النشر عند تحديث الفرع المحدد.

## قاعدة البيانات

ملف المخطط: `migrations/0001_initial.sql`

يتضمن:
- `categories` الفئات.
- `products` المنتجات والأسعار والمخزون.
- `product_images` صور المنتجات بترتيب مستقل.
- `orders` طلبات الزبائن.
- `order_items` تفاصيل كل طلب.

الأسعار تحفظ كأعداد صحيحة بالدينار العراقي، ولا تُستخدم الكسور العشرية. الترتيب يعتمد `sort_order`.

## إعداد Cloudflare Access

أنشئ تطبيق Access من نوع Self-hosted للمسارين `/admin/*` و`/api/admin/*`، واجعل سياسة Allow لبريد المالك فقط. أضف متغيرات Worker التالية في إعدادات البيئة كقيم سرية/خاصة: `CF_ACCESS_TEAM_DOMAIN` (مثل `team.cloudflareaccess.com`)، و`CF_ACCESS_AUD` (Application Audience Tag)، و`OWNER_EMAIL`. تتحقق واجهات الإدارة من توقيع JWT عبر مفاتيح Cloudflare العامة، ولا تعتمد على ترويسة بريد غير موثقة.

## الحماية والخصوصية

- فعّل Cloudflare Access على مسارات الإدارة واسمح ببريد المالك فقط.
- لا تضع كلمات مرور أو مفاتيح API في GitHub.
- لا تجعل جداول الطلبات متاحة لواجهات القراءة العامة.
- يجب أن يتحقق الخادم من الأسعار والمخزون عند إنشاء الطلب؛ لا تعتمد على السعر المرسل من المتصفح.
- لا تخزن صور المنتجات كـ BLOB داخل D1؛ استخدم روابط ملفات في مخزن ملفات مستقل مثل R2 عند الحاجة.

## ترحيل حماية المخزون

بعد نشر الكود، نفّذ `migrations/0002_inventory_triggers.sql` على قاعدة D1 الموجودة من Console مرة واحدة. هذا الترحيل يجعل خصم المخزون عند إنشاء الطلب واسترجاعه عند الإلغاء ذرياً داخل قاعدة البيانات.

## ما تبقى قبل التشغيل الفعلي

1. ضبط تطبيق Cloudflare Access ومتغيرات المالك في Cloudflare.
2. تنفيذ `0002_inventory_triggers.sql` على قاعدة D1 الحالية.
3. تشغيل CI والتأكد من نجاح فحوص TypeScript وESLint وبناء Next.js.
4. نشر Worker عبر حساب Cloudflare ثم تجربة طلب COD والتحقق من المخزون وحالات الطلب.
5. ربط رفع الصور بمخزن R2 عند الحاجة؛ النسخة الحالية تقبل رابط صورة مباشر.
