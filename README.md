# RETRO Store

متجر إلكترونيات وأجهزة ريترو باللغة العربية، مبني باستخدام Next.js 15 وCloudflare Workers وCloudflare D1.

## البنية الحالية

- GitHub: مستودع الكود وإدارة الإصدارات.
- Cloudflare Workers: تشغيل تطبيق Next.js عبر OpenNext.
- Cloudflare D1: قاعدة SQLite للمنتجات والفئات والطلبات والإدارة.
- العملة: الدينار العراقي (IQD).
- الطلبات: الدفع عند الاستلام، دون اشتراط حساب للزبون.
- الصور: روابط صور خارجية حالياً؛ يمكن إضافة R2 لاحقاً.

## ربط D1

ملف `wrangler.toml` يحتوي مسبقاً على binding باسم `DB` ومعرّف قاعدة البيانات الحالية `d6a1c5aa-767a-433c-b201-3745b7a2e329`. لا تنشئ قاعدة ثانية ولا تستبدل هذا المعرّف.

يقرأ التطبيق الاتصال من `getCloudflareContext().env.DB` داخل `lib/db.ts`. المسار `/api/health` ينفذ فحصاً للقراءة فقط: يتأكد من إمكانية تنفيذ SQL ومن وجود الجداول والفهارس والمشغلات الأساسية. عند الجاهزية يعيد:

```json
{"ok":true,"database":"connected"}
```

إذا أعاد الفحص حالة 503، فهذا يعني أن ربط D1 أو أحد عناصر المخطط غير جاهز؛ لا تعرض بيانات الإدارة أو الطلبات للعامة.

## الترحيلات — انتبه قبل التنفيذ

ملفات الترحيل:

1. `migrations/0001_initial.sql`: الجداول الأساسية للفئات والمنتجات والصور والطلبات وعناصر الطلب.
2. `migrations/0002_inventory_triggers.sql`: الفئات الابتدائية ومشغلات خصم المخزون وإعادته عند الإلغاء.
3. `migrations/0003_admin_roles_settings.sql`: حسابات الإدارة ورموز التحقق وإعدادات المتجر وسجل التدقيق.

**قاعدة D1 موجودة مسبقاً. لا تستخدم `wrangler d1 create`.**

قبل أي تغيير على قاعدة البيانات البعيدة:

1. افتح Cloudflare Dashboard وتأكد من الحساب والقاعدة `retro-store-db` ومعرّفها أعلاه.
2. أنشئ نسخة احتياطية/لقطة من قاعدة البيانات قبل الترحيل.
3. نفّذ `npm run db:remote:list` لمعرفة حالة سجل الترحيلات.
4. نفّذ `npm run db:remote:verify` وراجع أن الجداول التسعة والمشغلات الثلاثة والفهرس الفريد ظاهرة.
5. قارن أعمدة الجداول الموجودة بالمخطط في ملفات SQL، خصوصاً `orders` و`products`. وجود اسم الجدول وحده لا يثبت تطابق أعمدته.

إذا كانت الترحيلات الثلاثة مسجلة كمطبقة، لا تعِد تطبيقها. إذا كان سجل الترحيلات فارغاً أو كانت بعض ملفات SQL قد نُفذت يدوياً من لوحة D1، فلا تشغّل apply عشوائياً: راجع أعمدة الجداول أولاً لأن `CREATE TABLE IF NOT EXISTS` لا يصلح جدولاً قديماً بأعمدة مختلفة. بعد التأكد من تطابق المخطط، يمكن تنفيذ الترحيلات الناقصة بالأمر:

```bash
npm run db:remote:apply
```

ثم أعد تنفيذ:

```bash
npm run db:remote:list
npm run db:remote:verify
```

لا تنفذ ملف `0002_inventory_triggers.sql` منفرداً إذا كان مسجلاً مسبقاً في سجل Wrangler. أوامر الفحص لا تغيّر البيانات.

## التشغيل المحلي

المتطلبات: Node.js 20 أو أحدث، npm، وحساب Cloudflare عند استخدام D1 البعيدة.

```bash
npm install
npm run dev
```

لمعاينة التطبيق في بيئة Workers:

```bash
npm run cf-typegen
npm run preview
```

## أوامر D1

```bash
npm run db:remote:list
npm run db:remote:verify
npm run db:remote:apply
```

يجب تسجيل الدخول إلى Wrangler بحساب Cloudflare الذي يملك قاعدة البيانات قبل تنفيذ الأوامر البعيدة. لا تضع API tokens أو مفاتيح سرية في GitHub أو ملفات المصدر.

## النشر

بعد تأكيد D1 والترحيلات ومتغيرات البيئة:

```bash
npm run deploy
```

بعد النشر افتح `/api/health` وتأكد من استجابة `200` و`database: connected`، ثم اختبر إضافة منتج وطلب COD وإلغاء طلب والتحقق من تغير المخزون. لا تعتبر الموقع جاهزاً للإنتاج قبل هذه الاختبارات.

## Cloudflare Access وإعدادات الإدارة

أنشئ تطبيق Access من نوع Self-hosted لمسارات `/admin/*` و`/api/admin/*`، واجعل سياسة Allow لبريد المالك فقط. أضف متغيرات Worker التالية في إعدادات Cloudflare:

- `CF_ACCESS_TEAM_DOMAIN`
- `CF_ACCESS_AUD`
- `OWNER_EMAIL`
- `RESEND_API_KEY` عند استخدام إرسال رموز التحقق بالبريد.

تأكد من ضبط القيم السرية في إعدادات Worker وليس في المستودع.

## ملاحظات سلامة البيانات

- لا تجعل جداول الطلبات أو بيانات العملاء متاحة لواجهات القراءة العامة.
- يتحقق الخادم من الأسعار والمخزون من قاعدة البيانات عند إنشاء الطلب؛ لا يعتمد على السعر المرسل من المتصفح.
- مشغلات D1 تخصم المخزون عند إدخال عناصر الطلب وتعيده عند إلغاء الطلب.
- لا تخزن صور المنتجات كـ BLOB داخل D1؛ استخدم روابط أو R2.
- لا تعدّل بيانات الإنتاج يدوياً قبل أخذ نسخة احتياطية.
